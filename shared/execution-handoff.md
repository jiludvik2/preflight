# Working with an execution lead

This handoff connects Preflight preparation to your chosen implementation workflow.
Preparation returns its result to the selected lead. It does not start execution or require
an execution skill.

For a specialist handoff, read [Information the lead needs](#information-the-lead-needs) and
[Check the returned work](#check-the-returned-work). Read
[Continuing work already started](#continuing-work-already-started) when the handoff affects
in-flight work. The capacity section applies to the lead or delegate that dispatches agents,
not a specialist that only returns its result.

## One lead, two preparation skills

The controlling chat remains the execution lead. An already selected workflow, including issue
resolution, retains its loop. Do not start a second controller at a handoff. Preserve the selected
workflow's nonconflicting checks, independent review and permissions.
Use define-change when intended behavior or domain meaning is unsettled, and design-solution
when architectural or technical contracts need work. Do not invoke both automatically, or return to a document workflow for
routine coding choices already covered by the accepted contract.

The lead owns implementation planning, worktrees, progress, scheduling, parallel work,
verification, repair, review and implementation handoff. The preparation skills supply descriptions, governing
content and scoped gaps. They do not create a second implementation plan or execution controller.
For delegated preparation tasks, use [Preflight model assignments](model-selection.md).
Other workflows retain their execution and panel settings. A code sketch can shape types,
signatures and modules within the agreed solution, but does not accept a new architectural decision.
If a requested playbook conflicts with the agreed scope, resolve that explicitly rather than
quietly skipping its requirements.

## Plan delegation against current capacity

Before dispatch or follow-up, reconcile the whole agent tree in the existing execution record.
Include the lead, nested workers, retained identities and remaining essential roles. Use supported
inventory and runtime-limit information, recording its scope and observation time. Distinguish
running execution from retained threads and admission capacity. Missing information stays unknown;
completion or interruption does not establish that a slot was released. A local worker count is
not a whole-tree inventory.

Let the existing lead do coordination and synthesis where the applicable playbook permits it.
Prefer sequential exploration when adequate and label that fallback honestly. Plan genuinely
required reviewers before optional fan-out, without a fixed delegation quota or assumed reservation.
For independent review, use a fresh context that has not authored the change. Reuse a finished
reviewer only when the selected workflow permits it and independence still holds. Give that
reviewer the full current brief and revision, and count the actor once. An exposed development
actor cannot substitute for independent confirmation.

Before spending protected access or disclosing evidence, establish that each required independent
reviewer can participate through a neutral preparation assignment for that real review. Withhold
protected leads, interpretations and predictions. Record the actor, independence basis, acknowledgement
and preparation cost in the existing assignment and exposure records. Do not launch disposable agents
to probe capacity. Reconcile current inventory and recheck participation before actual dispatch or
follow-up; earlier creation is not a guarantee of execution. Reuse an immediately current neutral
acknowledgement when still applicable, rather than creating a loop of readiness probes. If the host
cannot separate admission from evidence delivery, keep the evidence withheld until a permitted
delivery path is established. Neither preparation nor a static validator reserves host capacity.

After admission rejection, stop spawning and record the exact failure. Reconcile the whole tree
before another admission attempt. Retry only after an observable change relevant to that failed
operation, such as an attributable host admission update. Changing caller, model, session or order,
or seeing a worker finish, does not establish that change. Apply the same rule to rejected follow-up.
Unavailable inventory does not prove zero capacity or justify repeated probes; absent a prior rejection,
one needed neutral assignment may establish participation within the existing allowance.

Preserve completed results, unfinished membership, actual and unknown exposure, and consumed costs.
Continue independent eligible work, or select the existing bounded stop and verified handoff.
Keep a required review gate closed when its reviewer cannot run. Scope that blocker to dependent
work; it neither discards partial results nor renews an allowance. The host owns admission and capacity
release. These instructions grant no thread-closure capability or runtime-limit override.

## Information the lead needs

A standalone preparation-skill invocation returns its result without starting an
execution workflow. For a handoff, keep the following information in the existing task record or
operation result, using source links rather than copied documents:

- The outcome and requested next activity.
- The parent objective and its source, current phase, verified progress, and next executable
  action within the user's authorization. Scope each blocker to the work it actually prevents.
  A local finding does not close or replace the parent objective.
- Actual governing sources and revisions, their affected scope and exclusions, and their
  acceptance status. Keep recovered observations and proposed interpretations distinct from
  those governing sources, following the shared evidence and document-purpose guidance.
- Affected contracts and interfaces, verification obligations, and material dependencies.
- Unresolved findings with the concrete uncertainty, affected work, next action, and what
  would settle each finding, following the [finding guidance](principles.md#actions-questions-and-scope).
- The operation, edit and [acceptance authority](principles.md#meaning-and-authority), plus
  applicable network, time, cost and execution restrictions.

These are content requirements, not a mandatory handoff form. Pass the relevant instructions
or this reference to the next lead, delegates, and resumed sessions. Delegation and resumption
grant no additional permission. Do not create a second plan or handoff file.

To find downstream work, start with relevant locators in the existing execution record or
project overview, then search the affected collections for stable source IDs, paths and scope.
Open matches to distinguish governing dependencies, proposals, historical evidence and
navigation; a match alone does not establish applicability or complete coverage. Missing
backlinks do not mean that designs, tests or implementation are missing. If discovery remains
incomplete, state the bounded search and its limits. Carry the useful locators into the existing
handoff rather than adding reciprocal links to governing documents or creating another index.

Include the [domain context and terminology](principles.md#useful-explanations) needed for
the assigned work. The lead carries it into each affected delegated task or resume point
and tells the recipient to read the governing definitions. Do not assume a worker
has loaded Preflight or knows the originating conversation.

For an investigation, also carry its decision question, the meaning of each measure, the
assumptions linking observation to impact, and any interpretation already reached with its
rationale and source. The result owns findings and interpretation; this handoff points to them.
Only an accepted domain or design artifact owns an enduring rule.

## Check the returned work

For changes to governing content, follow the
[upstream request and return check](principles.md#upstream-changes-and-return-checks).
Keep the original request and its resolution condition available to the recipient and the lead.
That guidance defines what the specialist returns and who checks it before closing the finding.
Specialist completion alone does not establish readiness. Independent work may continue while
dependent implementation awaits acceptance.

The lead reconciles overlapping or conflicting findings against governing sources before
presenting the combined result. Preserve material evidence, uncertainty and distinct closure
conditions while combining duplicate questions into one actionable question. Check changed
dependencies against current inputs. Reuse earlier checks only for the inputs they actually
examined; retain unaffected results rather than repeating the whole review.

Explain whether the combined result supports the requested next activity and any limits,
using the [completion guidance](principles.md#proof-proportional-to-the-claim).
Flag consequential assumptions and cross-document guarantees for the lead's review. For Draft and
substantive Revise, apply [independent challenge](independent-review.md). Reuse a qualifying existing
review instead of adding a duplicate. This adds no controller or human acceptance round.

Preflight returns preparation results to the selected implementation lead. Preparing a change does
not start implementation or accept governing documents. The caller or repository selects the
implementation workflow.

Preserve material contract obligations in the existing brief or execution record. For each, retain
the governing source and required behavior, expected interpretation and disposition, discriminating
example where needed, dependent work, evidence with its applicable revision, and remaining uncertainty.
Link the owning contract rather than copying it. The design defines the meaning and necessary proof;
preparation carries it forward; the execution lead checks closure against matching evidence. Do not
create a second obligation register or weaken specific proof into a generic test task.

During implementation and before calling it complete, the lead compares results with accepted
requirements, domain meanings, design commitments and ADR coverage, including material technology
roles and interfaces. Flag unplanned dependencies, unapproved roles, replacements and planned
technologies no longer used. A new dependency is not authorized merely because the code works.
Keep this check in execution and review, not in experimental tooling.

As part of the existing verification, check the resulting documents, contracts and
domain-facing code against those meanings. Retain clear engineering mappings and required
compatibility. Route unresolved meaning changes through the existing upstream return check;
do not silently rename concepts or accept a proposal to make the implementation agree.
This adds no review round and grants no edits to a read-only operation.

## Continuing work already started

Completing recovery completes the preparation assignment, not the parent implementation goal.
The lead assesses that goal and continues useful authorized work, using the existing result,
execution record and checkpoint. A recovered description supplies evidence, not new authority.

When changed meaning or design affects an in-flight implementation, reconcile its existing
execution record with code, delivery records and current verification evidence. Retain
completed results that still hold; identify only the results invalidated by the change.
Explain the effect on remaining work, dependencies and acceptance checks.

Give a fresh implementer one resume point in that record: the next executable action, the
prerequisites for dependent work, and the original objective or checkpoint to resume afterward.
Link the relevant branch, worktree, commits or PRs where they exist. Identify local-only
changes explicitly; another checkout cannot rely on them. Never invent a commit or progress.

If the resume point is uncertain, name the evidence gap and a bounded reconciliation action.
Do not claim execution readiness. A documentation-only change need not alter execution.
Revising progress does not accept requirements, architecture, designs or new scope.

## Example handoff

> Pass this accepted design and its governing requirements to the existing implementation lead.
> Carry the domain meanings, unresolved questions, and proof obligations into the existing task record.

An end-to-end execution check must exercise the selected workflow and actual project result.
Reading this reference or passing package validation alone does not prove agent behavior.
